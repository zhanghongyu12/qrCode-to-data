# 并行分工规则 (Parallel Split Rules)

## 适用场景

任一角色在工作过程中发现自己被瓶颈卡住、有独立工作块可以切出去时，可发起一次"并行分工"。不是工作流的固定环节，不强制触发。最终是否拆分由使用者决定，发起方只产出请求说明，不擅自启动并行。

与现有机制的关系：
| 机制 | 适用场景 | 规则文件 |
|------|---------|---------|
| 顺序交接 | 单向流转（PM → Architect → Developer） | workflow.md + 各角色文件 |
| 双向协作 | 两个不同角色间来回对话 | coordination_rules.md |
| 结构化辩论 | 两个 Expert 深度辩论 | ExpertDebate/rules.md |
| 并行分工 | 同角色实例间按文件隔离并行（本规则） | parallel_split_rules.md |

四者独立，互不干扰。

---

## 完整流程

### 1. 发起方自检

发起方跑硬门禁自检（四条逐条判定），再写反问。四条有任一不满足，或反问写不出具体轮次差，直接不出请求，继续单窗口做。

### 1.5 工作空间检测

发起方检测当前环境是否支持 worktree（执行 `git worktree` 确认可用性），根据结果在拆分请求说明的「工作空间方案」区块写明走哪条路。

### 2. 产出拆分请求说明

发起方写拆分请求说明，在输出中报告"已产出并行拆分请求，请使用者审阅"。不创建 session 目录，不动任何文件。

### 3. 使用者审阅

- **批准** → 发起方创建 session 目录，补全 context.md 其余区块，使用者将通知话术粘贴至辅助窗口
- **不批准** → 发起方继续单窗口串行，不创建 session

### 4. 两路并行工作

两路在各自隔离的工作空间（worktree 或 clone）中、不同分支上独立工作，互不干扰。辅助方按契约编码，契约变更走 contract_log.md。

### 5. 交付与收尾

见下文"交付与收尾"。

## 硬门禁

四条全满足才允许产出请求：

1. **可切出的独立任务 ≥ 4 个**（或 3 个但每个预估工作量 ≥ 4 小时）：少于这个数，协调开销（写文档 + 对方起步）很可能超过省下的时间
2. **文件级隔离可达成**：能列出两份不重叠的文件路径清单，列不出来就不切
3. **契约面 ≤ 8 个方法签名**：超过这个数，契约文档本身就变成一个大工程，而且漂移风险急剧上升
4. **发起方保留侧至少有 1 个任务能不等对方独立推进**：如果切完之后自己还得等对方出结果才能动，那不是并行，是换了个地方排队

## 反问

发起方必须显式写一句，须包含以下要素（不锁句式）：

- 单窗口串行预计轮数（量化）
- 切出后预计轮数（量化）
- 省多少轮（量化差值）
- 理由（具体说明瓶颈在哪）

写不出具体轮次差或理由含糊，不出请求。

## 拆分请求说明

放在 context.md 顶部，供使用者快速判断是否批准。三部分：

1. **一句话结论**：建议拆分 / 不建议拆分
2. **拆分理由**（3-5 句）：瓶颈在哪、切出去的是什么、切完后两路各自做什么、预计省多少时间
3. **使用者决策点**：固定问句——"请确认是否执行本次拆分。若确认，将通知话术粘贴至辅助窗口；若否，发起方继续单窗口串行。"

4. **工作空间方案**：根据工作空间检测结果写明：
   - **支持 worktree**：给出命令 `git worktree add ../{项目名}-b feature/{协作名}-b`，B 路在独立目录工作
   - **不支持 worktree**：声明"当前环境不支持 worktree，采用独立 clone 方式"，贴上项目仓库地址和 B 路分支名
   - 同一文件夹多窗口并行已禁止，不得使用

## 交付状态机

辅助方交付区块维护状态字段，状态流转：

```
未开始 → 进行中 → 已交付
               ↗        ↘
         待修订          异常中断（人工标注）
```

约束：
- 辅助方必须先写完交付说明全部内容，最后一步才把状态改为"已交付"
- "已交付"后若发现问题可回退至"待修订"（见下文"交付回退"）
- "异常中断"只能由人工写入，AI 不得自行标注
- 发起方只认"已交付"这一个状态作为收尾信号

自动化验证门禁：
- 状态改为「已交付」前，必须在交付区块附自动化验证通过证据（贴输出末尾几行），无证据不得标「已交付」
- 验证范围按项目技术栈配置：编译 / 构建 / lint / 单元测试，不限于编译
- 依赖未就绪时允许暂跳验证，但交付前必须全量通过
- 非 JVM 项目用对应命令替代（如 `npm test`、`cargo build`、`go test`）
- 交付区块的「模块测试结果」字段不得为空，必须贴实际输出

## 交付与收尾

### 三种情况

### 四种情况

**情况一：辅助方先完成，发起方还在做**
- 辅助方写完交付说明，状态改为"已交付"，输出"已交付，等待发起方收尾"，结束
- 不需要通知发起方。发起方做完后读 context.md 交付区块，状态为"已交付"则直接收尾
- 零人工介入

**情况二：发起方先完成，辅助方还在做**
- 发起方读 context.md 发现交付状态不是"已交付"，写完成说明（发起方完成状态改为"已完成"），输出通知话术给辅助方
- 人工将话术粘贴至辅助方窗口
- 辅助方完成后写交付说明，状态改为"已交付"
- 发起方回来收尾（若窗口仍开着则自行读取；若已关闭，人工唤起发起方收尾）

**情况三：双方几乎同时完成**
- 发起方做完后读 context.md 发现辅助方已"已交付"，直接收尾
- 零人工介入

**情况四：发起方主动取消**
- 发起方在 context.md 标记状态为"已取消"，写明取消原因
- 辅助方读到"已取消"后停止工作，不再修改代码
- 已完成的代码保留在从分支，不合并到主分支
- 人工决定是否保留从分支以备后续使用

### 交付回退（已交付 → 待修订）

当发起方在收尾阶段发现辅助方交付的代码存在问题时：

- 触发条件：git 合并冲突 / 全量测试失败 / 契约一致性检查不通过
- 发起方在 context.md 将交付状态从"已交付"改为"待修订"，写明问题描述
- 输出通知话术给辅助方（人工粘贴）
- 辅助方收到后读 context.md「待修订」问题描述，修复后将状态改回"已交付"
- 修复期间辅助方在从分支工作，不碰主分支

### 辅助方恢复流程（中途掉线后重新加入）

辅助方因窗口关闭、崩溃或其他原因中断后重新启动时：

1. 读 context.md 获取当前 session 状态和文件归属
2. 读 context.md「辅助方交付」区块的「实现摘要」获取已完成进度
3. 读 contract_log.md 全部条目，获取最新契约变更
4. `git merge feature/{协作名}` 拿到发起方最新代码
5. 确认当前分支正确（`git branch`）、worktree/clone 目录正确（`pwd`）
6. 从断点继续编码，无需从头开始

### 发起方收尾步骤

**第一组：合并验证**
1. 读交付区块确认状态为"已交付"
2. `git diff 主分支...从分支 --stat` 确认改动范围与交付区块的文件清单一致
3. 合并从分支到主分支（文件级隔离正常不冲突；若冲突说明隔离被打破，记入 contract_log.md 并人工介入）

**第二组：一致性检查**
4. 跑全量测试，确认两路合在一起能通过
5. 逐条核对接口契约区块签名与实际代码一致（契约一致性检查，最后一道防线）
6. 确认 contract_log.md 无「待确认」条目

**第三组：清理**
7. 统一更新正式文档（06_tasks.md 任务状态、CHANGELOG、07_decisions.md）
8. `git worktree remove` 清理辅助方工作空间（如使用 worktree 模式）
9. 删除临时 session 目录
10. 输出收尾完成通知告知使用者

## 契约锁定约束

**排他声明**：接口契约只认 context.md「接口契约」区块和 contract_log.md。其他任何文件（包括临时修复计划、PR 描述、聊天记录、对话历史）均无契约约束力。发起方不得在上述两个文件之外的地方写契约变更。辅助方只对上述两个文件负责，不负责追踪其他文档中的契约信息。
context.md 接口契约区块 = 最新状态（主），contract_log.md = 变更日志（从）。发起方追加 contract_log.md 后必须同步更新 context.md 接口契约区块，确保两者一致。

**发起方约束**：接口契约区块里已登记的每个签名都是契约，发起方在实现过程中不得单方面修改。若实现时发现某个签名写不通，必须先做两件事再动代码：①在 contract_log.md 追加一条，写明"旧签名 → 新签名 + 原因"；②在输出中显式报告"契约已变更，请通知辅助方"。追加记录后才可以改代码。每次输出时，若本轮未改契约，也需明确说一句"本轮未变更契约"。此条优先级高于任何编码判断。

**辅助方约束**：辅助方依赖的接口签名以 context.md「接口契约」+ contract_log.md 两个区块为准。每次开工（收到新指令或恢复工作时），先读 contract_log.md 全部条目，确认无「待确认」状态的契约变更后，再开始编码。若有「待确认」条目，先等发起方确认再动相关代码。**契约同步**：辅助方每 30 分钟（或每 3 次 commit）执行 `git merge feature/{协作名}` 拉取主分支最新代码，并检查 contract_log.md 顶部「最后更新」时间戳是否有变化。若编译报错涉及对方层的接口，立即 merge + 读 contract_log.md，而不是自己猜原因或改接口。若发现代码实际签名与契约不符，不得自行调整接口，应在 contract_log.md 追加一条问询（标注"待发起方确认"），然后继续做当前不依赖该接口的其他任务。辅助方无权修改对方文件和接口定义。

**双向归属约束**：文件归属是双向的——发起方同样不得修改辅助方可写路径下的文件。发起方发现辅助方文件的编译错误时，不得直接上手修，应在 contract_log.md 追加一条问询（标注「待辅助方确认」），然后继续做其他不涉及该文件的任务。只有合并阶段发起方才碰辅助方文件，且仅限解决 git 冲突。辅助方发现发起方文件的编译错误时，同理：问询而非上手改。

**文档更新权**：只有发起方有权限更新正式文档（06_tasks.md / CHANGELOG / 07_decisions.md），辅助方不碰。

## 冲突处理

### 开发中发现（一方需要碰对方文件）

发现方立即停手，不碰那个文件，在 contract_log.md 追加一条，类型标"文件冲突"，写明需要修改的文件、归属对方、原因。然后分两种走法：

- **能通过契约绕开**：冲突的本质是"我的新东西需要对方文件配合注册/接线"。发现方在 contract_log.md 写明请求，然后继续做其他不涉及冲突的任务。对方在自己的节奏里读到记录后处理，处理完标"已解决"。双方不中断，异步传递。
- **绕不开**：同一文件两边都要改业务逻辑，没有契约能绕开。发现方在 contract_log.md 标"需人工介入"，然后继续做不涉及冲突的其他任务。等双方把能做的都做完了，人工介入协调——判断怎么分（文件重新划归某一方，或一方等另一方改完再接），结果写进 contract_log.md，双方继续。

### 合并时发现（git merge 冲突）

发起方收尾合并分支时撞上 git conflict。发起方有合并权，先尝试自行解决冲突：

- 如果是公共文件冲突（入口注册、配置、路由表），发起方直接合并两边改动
- 如果涉及对方文件的具体业务逻辑（发起方看不懂对方为什么那么写），发起方不得猜着改，在 contract_log.md 追加一条标"合并冲突待确认"，保留冲突状态，等辅助方或人工确认

### 要不要打断对方

取决于"这个冲突会不会让对方白费大量工作"。大多数情况下不会——文件隔离保证两路主要工作独立，冲突只是边界摩擦，靠 contract_log.md 异步传递即可，不用中断对方。

只有一种情况需要打断对方：发现方确认契约本身不可行，对方继续做会全部白写。这种情况说明拆分评估有误，走"异常中断"而不是常规冲突处理。

### 公共文件预防

文件归属表里的"公共文件"行不能空着。拆分时如果识别到有公共文件（build.gradle、DI module、路由表等），必须写明谁来改、什么顺序改。合并时才撞上公共文件，说明拆分评估漏了，走"合并冲突"流程。
**建议（非强制）**：公共文件尽量不在并行阶段直接修改，各方在独立注册文件/配置文件中声明，合并阶段由发起方统一拼装。在高耦合项目中此建议可能不可行，以"写明谁来改、什么顺序改"为底线。

## 提交纪律与工作空间

### 主从分支结构

```
feature/{本次协作名}        ← 主分支（发起方 A 路直接开发）
└── feature/{本次协作名}-b   ← 从分支（B 路从主分支切出）
```

- 主分支：发起方直接在此开发，有合并权、文档更新权
- 从分支：辅助方从主分支切出，在此开发
- 契约同步：A 路在主分支 commit 后，B 路 `git merge feature/{协作名}` 拿到最新
- 收尾：发起方把从分支合并回主分支
- 如需三路扩展：B、C 各自从主分支切出，各自合并回主分支

### 提交纪律

- 每完成一个任务项立即 commit，不留未提交改动在工作区
- 切换分支前必须 commit 或 stash
- 交付状态改为「已交付」前，所有改动必须已 commit
- commit 用 `git add {具体文件}`，禁止 `git add .` 或 `git add -A`（避免卷入对方改动）

### 工作空间纪律

- 同一文件夹多窗口并行**已禁止**——git 工作区只有一份，切分支两个窗口同时变，未提交改动会被对方操作误伤
- **worktree 模式**（默认推荐）：`git worktree add ../{项目名}-b feature/{协作名}-b`，两路在各自物理目录工作，共享 .git
- **clone 模式**（worktree 不可用时）：B 路 clone 项目后切到从分支，A commit 后需 push，B pull 拿到


### 辅助方开工自检

辅助方开工（首次加入或恢复工作时）须逐条确认后才开始编码：

1. 当前目录是 worktree/clone 目录（不是发起方主目录）：`pwd` 确认
2. 当前分支是 feature/{协作名}-b（不是主分支）：`git branch` 确认
3. git author 已设置：`git config user.name` 确认
4. 读 contract_log.md 全部条目，确认无「待确认」变更
5. 工作区干净：`git status` 确认无残留改动
6. 以上全部通过后，再开始编码

此清单为规则正文，通知话术中只需引用"请执行开工前自检"。

## 已知限制

| 限制 | 说明 |
|------|------|
| **三路扩展** | 当前版本仅支持双路并行，三路扩展协调机制待设计 |
| **.git 锁竞争** | worktree 共享 .git，并发 commit 可能遇锁错误，重试即可 |
| **共享测试资源** | 两路并行跑测试时注意端口、文件路径、构建缓存隔离 |

## 方法论：行为层 vs 形式层

规则约束分两层：
- **行为层**：约束直接改变可观察的行为决策，且出错不可逆或高修复成本——应保留
- **形式层**：约束只改变表达格式或仪式，不改变决策本身——应降为要素约束（划定"必须包含什么"），不锁"必须按什么格式"

新增规则时优先评估其属于哪一层。
