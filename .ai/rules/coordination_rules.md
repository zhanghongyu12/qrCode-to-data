# 跨角色协作规则 (Coordination Rules)

## 适用场景

当两个角色需要**双向对话**（而非单向交接）时，使用本规则。

典型场景：
- Architect ↔ Designer：并行设计阶段的交叉确认
- Developer ↔ Reviewer：回环流程中的问题修复与复审
- 任意两个角色：需要讨论而非直接决策的冲突

单向交接（如 PM → Architect）不需要本规则，通过 `docs/` 正式文档 + `06_tasks.md` 状态区块流转即可。
结构化辩论（两个 Expert 深度辩论）使用 `.ai/rules/ExpertDebate/rules.md`，不使用本规则。

---

## 设计原则

| 原则 | 含义 |
|------|------|
| **纯文件驱动** | 所有通信通过文件完成，不依赖任何工具的私有 API |
| **人工触发** | AI 是请求-响应模式，无法自动监听文件变化。每次需要角色响应时，由人工通知 |
| **角色自带通知话术** | 角色写完消息后必须输出可复制粘贴的通知文本 |

核心思路：**文件是通信记录，人是触发信号。**

---

## 权限说明

`.session/` 目录是**协作工作空间**，由本规则管辖，不受角色文件中「权限边界」和「铁律」的约束。
铁律约束的是 `docs/` 下的项目文档；session 文件是临时协调空间。

| 文件 | 写权限 |
|------|--------|
| `board.md` | 所有参与角色可追加消息（append-only，不可修改已有消息） |
| `context.md` | 任一参与角色可更新状态字段（如"进行中"→"已升级"→"已结束"） |

---

## Session 结构

### 目录结构

```
.session/
  {session_id}/           ← session_id 格式：YYYYMMDD + 两位序号（如 2026071801）
    context.md            ← session 背景
    board.md              ← 消息板（append-only）
```

> session_id 规则与 ExpertDebate 一致。一个 session 要么是协作，要么是辩论，由 context.md 的"类型"字段区分。

### context.md 模板

```markdown
# Session 背景

> Session ID: {session_id}
> 类型: 协作
> 创建时间: YYYY-MM-DD
> 创建者: 人工
> 关联阶段: （如 阶段 3-4 并行设计）
> 状态: 进行中（可取值：进行中 | 已升级 | 已结束）

## 讨论背景
（描述为什么需要这次协作）

## 参与角色
- 角色A（已加入）
- 角色B（待加入）
- 角色C（升级时按需加入，可选）

## 输出目录
.session/{session_id}/
```

### board.md 消息格式

单文件，append-only，按时间顺序追加。每条消息格式：

```markdown
---

## MSG-XXX: 消息标题

- 编号: MSG-XXX
- 时间: YYYY-MM-DD HH:MM
- 发送者: 角色名
- 接收者: 角色名（或 ALL）
- 类型: 请求确认 | 请求反馈 | 回复 | 提问 | 通知 | 结论 | 升级
- 关联文档: docs/XX_xxx.md
- 期望操作: 阅读并回复 | 阅读并确认 | 阅读即可
- 回复: MSG-YYY（仅回复类消息填写）

### 正文

（消息内容）
```

**消息编号**：从 MSG-001 开始递增，不复用。

**消息类型**：

| 类型 | 用途 | 是否期望回复 |
|------|------|-------------|
| 通知 | 单向告知 | 否 |
| 请求确认 | 请求对方确认某件事 | 是 |
| 请求反馈 | 请求对方给出意见 | 是 |
| 回复 | 对之前消息的回复（必须引用原消息编号） | 视情况 |
| 提问 | 向对方提出问题 | 是 |
| 结论 | 讨论达成的最终结论 | 需对方确认 |
| 升级 | 请求第三方角色介入裁决 | 是（第三方角色） |

---

## 协作流程

### 1. 创建 session

人工完成以下操作：
1. 创建 `.session/{session_id}/` 目录
2. 填写 `context.md`（类型标为"协作"，写明背景、参与角色、关联阶段）
3. 创建空的 `board.md`

### 2. 角色加入

人工在角色的窗口中发送指令（可直接使用下方"通知话术模板"的加入格式）。
角色读完 context.md 和 board.md 后，开始工作或回复消息。

### 3. 角色间对话

```
角色A 完成工作 → 追加消息到 board.md → 输出通知话术
→ 人工复制话术，粘贴到角色B 的窗口
→ 角色B 读 board.md → 追加回复 → 输出通知话术
→ 人工复制话术，粘贴到角色A 的窗口
→ ...反复直到对齐，或触发升级（见第 4 节）
```

人工每次只需做一件事：**复制角色输出的通知话术，粘贴到另一个角色的窗口**。

### 4. 升级与第三角色介入（当讨论无法收敛）

当双方在某个分歧点无法对齐时，不要无限循环。满足以下任一条件即应升级，不再继续辩。

**升级触发条件（任一满足）**

1. **同一分歧点来回超过 3 轮，且无新论据** — "轮"指双方各发一次。若某方要写的内容与自己两轮前实质相同，即在重复而非推进
2. **分歧事项超出这两个角色的职责边界** — 如两个 developer 争一个只有 PM 能定的产品需求，或该 Architect 拍板的架构走向。角色在写下一条前先自问：这个决策在我的职责范围内吗？不在，就升级
3. **分歧是价值取舍，不是事实分歧** — "安全 vs. 速度""一致性 vs. 可用性"这类无对错、只有取舍的问题，靠讨论永远无法收敛

**还不用升级的信号**（继续讨论即可）：
- 每轮都有新论据、新信息
- 分歧在收窄，从大问题聚焦到一个小点
- 一方在问澄清问题，而非重申立场
- 还在产出具体方案

**升级动作**

1. 不再写新论据，改写一条"升级"类型消息：
   - 标记核心分歧点
   - 简述双方立场
   - 指明需要哪个角色介入裁决（如"需 PM 裁决"），或标注"需人工裁决"
2. 将 context.md 状态改为"已升级"
3. 输出通知话术——使用人员复制后粘贴到被请求角色的窗口

**第三角色加入**

- 第三角色定位：**裁决那个具体分歧点**，不是常驻成员。裁完、原两方对齐后，其任务即结束，不参与关闭确认
- 第三角色加入后：先读 context.md 与 board.md 了解升级上下文，再发"回复"类型消息给出意见或裁决
- 原两方围绕第三角色的裁决对齐，确认后按第 5 节流程关闭

**升级链（逐级上升，每步有明确出口）**

```
角色对齐 → 不收敛 → 升级给有权角色（如 PM/Architect）→ 还不收敛 → 人工裁决
```

- 第 2 条触发条件（越界分歧）升级目标往往是另一个角色，不一定要人亲自来
- 第 3 条触发条件（价值取舍）才真正需要人拍板——没有哪个角色有绝对权威

### 5. 结束 session

**关闭权：任一角色均可关闭**，但关闭必须经过对方单独确认。真正的安全闸是「确认」这一步，不是「只能发起方关」这条限制。

流程（三步，缺一不可）：
1. 某方角色写入"结论"类型消息（对本次讨论的最终总结），输出通知话术告知对方确认
2. 对方确认后，**单独**回复一条"确认"消息——确认与结论是两条独立消息，不可合并写入同一条
3. 写结论的那方收到确认后，**自行**将 context.md 状态改为"已结束"——不需要人工干预
4. 如有需要，将结论同步到 `docs/07_decisions.md`
5. 关闭 session 的角色输出最终通知，告知使用人员 session 已关闭

> 关闭方判断所有问题讨论完毕即可关闭 session，无需人工确认。关闭时输出：
> ```
> ✅ Session {session_id} 已结束。
> 所有问题已对齐，结论已记录在 board.md 中。
> 如需查阅，读取 .session/{session_id}/board.md。
> ```

**边角情况**：若一方写结论想关，另一方有分歧——分歧本身就是未决内容，不发"确认"，而是把分歧写进 board.md，会话继续。此时不应硬关；若分歧无法调和，走第 4 节升级流程。

## 通知话术模板（核心）

**角色每次向 board.md 写入消息后，必须在对话输出中附上通知话术。绝对不能写完消息就结束。**

### 标准格式

```
✅ 已向 .session/{session_id}/board.md 写入消息 MSG-XXX

📋 下一步操作：
请切换到 {接收角色} 的窗口，复制粘贴以下内容：

──────────────────────────────
你是 {接收角色}。请加入 session {session_id}。
读取 .session/{session_id}/board.md，
找到发给你的消息（MSG-XXX），处理后回复。
──────────────────────────────
```

### 通知话术三要素

1. **去哪个窗口** — 明确写出接收角色名
2. **可复制粘贴的完整文本** — 使用人员不需要自己编辑
3. **消息编号** — 告诉对方该读哪条消息

### 根据消息类型的变体

通知文本的最后一行根据消息类型有所不同：

| 消息类型 | 通知文本末尾 |
|---------|-------------|
| 请求确认 / 请求反馈 / 回复 / 提问 | 找到发给你的消息（MSG-XXX），处理后回复。 |
| 结论 | 找到 MSG-XXX（结论），确认无误后回复"确认"。双方确认后，此 session 结束。 |
| 升级 | 找到 MSG-XXX（升级请求），你是被请求介入的角色。读 context.md 与 board.md 了解分歧后，给出你的裁决。 |
| 通知（不需要回复） | 找到发给你的消息（MSG-XXX），阅读即可，无需回复。 |

### 角色首次加入 session 的话术

当使用人员需要让一个角色首次加入 session 时，使用以下话术：

```
──────────────────────────────
你是 {角色名}。请加入 session {session_id}。
先读 .session/{session_id}/context.md 了解背景，
再读 .session/{session_id}/board.md，
找到发给你的消息（MSG-XXX），处理后回复。
──────────────────────────────
```

## 与其他规则的关系

| 机制 | 适用场景 | 规则文件 |
|------|---------|---------|
| 顺序交接 | 单向流转（PM → Architect → Developer） | workflow.md + 各角色文件 |
| 双向协作 | 角色间来回对话（本规则） | coordination_rules.md |
| 结构化辩论 | 两个 Expert 深度辩论 | ExpertDebate/rules.md |
| 并行分工 | 同角色实例间按文件隔离并行 | parallel_split_rules.md |

四者独立，互不干扰。
