# Document Rules (文档规范)

## 通用原则

- 文档是项目的一等公民，与代码同等重要
- 文档更新与代码变更应同步提交
- 文档面向 AI 协作，需结构化、可解析
- 使用 Markdown 格式
- **铁律：不得越界写入。** 每个角色只能修改各自「权限边界」中「允许修改」列表内的文件。任何不在列表中的文件，无论理由多么充分，都不得修改。如需触碰其他角色的文档，必须通过 `docs/07_decisions.md` 记录冲突并等待人工确认，绝对禁止自行越界写入。

---

## 文档编号体系

```
00_idea.md           ← 产品想法（PM 维护）
01_prd.md            ← 产品需求文档（PM 维护）
02_architecture.md   ← 系统架构设计（Architect 维护）
03_database.md       ← 数据库设计（Architect 维护）
04_api.md            ← API 设计（Architect 维护）
05_ui.md             ← UI 设计（Designer 维护）
06_tasks.md          ← 任务清单（全员可更新）
07_decisions.md      ← 决策记录（全员可追加）
08_review.md         ← 审查报告（Reviewer 维护）
09_test_report.md    ← 测试报告（Tester 维护）
CHANGELOG.md         ← 变更日志（Developer 维护）
```

### 编号规则

- 00-05 为设计阶段文档，编号反映流程顺序
- 06-08 为执行阶段文档
- 09 为测试阶段文档
- 编号一经确定，在项目生命周期内尽量保持稳定；如因文档拆分或合并需要调整，须在 07_decisions.md 中记录变更原因和影响
- 06_tasks.md 维护者为全员可更新，其中项目状态区块由当前阶段负责角色更新

## 文档模板要求

### 每份文档必须包含

```
# 文档标题

> 状态：[草稿 | 评审中 | 已确认 | 已归档]
> 最后更新：YYYY-MM-DD
> 维护者：[角色名]

## 正文内容
...
```

### 状态流转

```
草稿 → 评审中 → 已确认 → 已归档
```

- 只有"已确认"状态的文档才能作为下游输入
- "草稿"状态的文档可以被任意修改
- "已确认"状态的文档修改需要记录到 07_decisions.md

## 决策记录规范 (07_decisions.md)

每条决策记录格式：

```
## DEC-XXX: 决策标题

- 日期：YYYY-MM-DD
- 决定：
- 原因：
- 影响：
- 替代方案：
- 最终选择：
```

### 规则

- 决策编号递增，不复用
- 已确认的决策不可删除，只能标记为"已废弃"
- 新决策与旧决策冲突时，必须引用旧决策编号

## 任务清单规范 (06_tasks.md)

### 任务格式

```
## TASK-XXX: 任务标题

- 状态：[待办 | 进行中 | 已完成 | 已阻塞]
- 优先级：[P0 | P1 | P2 | P3]
- 负责角色：[角色名]
- 关联需求：PRD 章节 / DEC-XXX
- 估算：[人时/天数]
- 依赖关系：[TASK-XXX | 无]
- 描述：
- 验收标准：
```

### 规则

- 任务编号递增，不复用
- 任务状态变更时更新时间戳
- 已完成任务保留记录，不删除
