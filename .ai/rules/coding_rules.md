# Coding Rules (编码规范)

## 通用原则

- 可读性优先：代码是写给人看的，其次才是机器执行的
- 单一职责：每个函数/类/模块只做一件事
- 命名清晰：变量名、函数名、类名应自解释，避免缩写
- 避免过早优化：先正确，再高效
- DRY 原则：不要重复自己，但也不强制抽象，三次重复才考虑提取

---

## 代码风格

### 命名规范

- 变量/函数：使用有意义的名称，避免 `a`, `b`, `tmp` 等无意义命名
- 常量：全大写 + 下划线，如 `MAX_RETRY_COUNT`
- 类名：大驼峰，如 `UserService`
- 文件名：遵循项目语言惯例（Python 用 snake_case，JS/TS 用 camelCase 或 kebab-case）

### 注释规范

- 只在复杂逻辑处添加注释，解释"为什么"而非"是什么"
- 避免无意义注释，如 `# 设置 x 为 10`
- 公共 API / 复杂算法必须有文档注释
- TODO 格式：`// TODO(角色): 描述` 或 `# TODO(角色): 描述`

### 错误处理

- 不要吞掉异常（空 catch/except）
- 错误信息应可追踪，包含上下文
- 区分可恢复错误和不可恢复错误
- 边界条件必须处理（空值、零值、溢出等）

---

## 文件组织

- 单文件不超过 300 行（软限制，超出应考虑拆分）
- 单函数不超过 50 行（硬限制）
- 缩进层级不超过 4 层
- 模块间依赖应单向，避免循环依赖

---

## 测试规范

- 每个公共函数必须有对应测试
- 测试命名：`test_<被测函数>_<场景>` 或 `describe('<模块>') → it('<场景>')`
- 测试应独立，不依赖执行顺序
- 使用 AAA 模式：Arrange → Act → Assert
- Mock 外部依赖，不 Mock 被测对象本身

### 测试目录结构

测试代码按以下目录分层，写入归属为强制约定：

| 子目录 | 写入归属 | 性质 |
|--------|---------|------|
| `tests/unit/` | Developer 独占 | 单元测试，白盒 |
| `tests/integration/` | Tester 独占 | 集成测试，黑盒 |
| `tests/e2e/` | Tester 独占 | 端到端测试，黑盒 |

双方均可读全部子目录（跑全量测试需要）。不采用分层的小项目需在 `docs/07_decisions.md` 记豁免说明。

## Git 提交规范

### Commit Message 格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

### Type 列表

- feat: 新功能
- fix: 修复 Bug
- docs: 文档变更
- style: 代码格式（不影响功能）
- refactor: 重构
- test: 测试相关
- chore: 构建/工具/依赖
- perf: 性能优化

### 规则

- subject 不超过 50 字符
- body 每行不超过 72 字符
- 一个提交只做一件事
- 不在提交中混入无关变更
