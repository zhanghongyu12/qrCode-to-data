## 1. 产品概述

### 产品名称

qrCode-to-data（暂定名，沿用项目名；后续可另立正式品牌名）

### 产品定位

一个通过二维码在设备间传输数据/文件的命令行（CLI）工具：默认用纯二维码光学传输（无需网络/蓝牙/USB），两端同网时自动切换 WiFi 直传加速；并支持用手机作为离线中转站，在隔离的两台电脑间摆渡数据。目标是为开发者/运维与安全敏感场景提供"零网络依赖、零配置、兼顾速度、时间解耦"的一体化传输方案。

### 产品目标

- **短期目标（MVP）**：在终端用一条命令完成"屏幕发、摄像头收"的点对点纯光学传输，覆盖文本与文件两类载荷，具备喷泉码纠错与完整性校验，可在空气隔离、无 GUI/无外设环境下可靠还原数据。
- **长期目标**：形成"纯光学为主 + 同网自动加速 + 手机离线中转"三合一的完整 CLI，按场景自动组合三条能力，成为隔离/弱网环境下的通用数据传输工具。

### 初步技术倾向（记录自想法，非正式选型）

> 说明：以下内容来自 `docs/00_idea.md` 的技术初步想法，PRD 仅如实记录，不构成选型结论；最终技术选型由架构阶段决定。

- 语言：倾向 Go（单二进制 CLI、二维码库成熟，参考 txqr），备选 Python（原型快）
- 纠错码：RaptorQ（RFC 6330）或 LT 码（如 gofountain）
- 二维码生成/解析：go-qrcode / ZXing / fast_qr
- 扫描：系统摄像头 + ZXing
- WiFi 直传：HTTP 临时服务 + 二维码承载连接信息（参考 qrcp）
- 手机端：移动网页（PWA，浏览器打开即用、可离线），复用浏览器摄像头扫码 + 屏幕播放

## 术语表

| 术语 | 定义 |
|------|------|
| 载荷（Payload） | 本次传输的数据内容，分为"文本"与"文件"两类。 |
| 纯光学传输 | 数据仅经"屏幕显示 → 摄像头采集"这一光学通道传递，不经网络/蓝牙/USB。 |
| 二维码动画序列（QR 流） | 将较大数据切块后逐块编码为二维码并按序连续播放，接收端连续扫描还原。 |
| 喷泉码（Fountain Code / FEC） | 把数据编码为大量带冗余的编码块（"水滴"），接收端收够任意足量不同块即可无损还原，天然抗漏帧、抗顺序错乱，无需 ACK/重传。本项目倾向 RaptorQ / LT 码。 |
| 同网加速 | 两端处于同一局域网时，二维码仅用于握手交换连接信息，实际数据走 WiFi 直传。 |
| 手机中转（摆渡） | 手机浏览器打开移动网页，先扫码接收并暂存数据，再在另一台设备前扫码发出，实现离线数据摆渡。 |
| 完整性校验 | 通过 CRC / 哈希等手段对还原后的数据做一致性校验，确保无损还原。 |

## 5. 用户场景

### 场景 1: 点对点纯光学传输（空气隔离机导出日志）

**前提条件：** 发送机 A（有屏幕）与接收机 B（有摄像头）物理相邻，均不联网、无蓝牙/USB；双方已安装本工具。

**操作流程：**
1. A 机在终端执行 send 命令，指定要发送的文件/文本，屏幕开始播放二维码动画序列。
2. B 机执行 receive 命令，将摄像头对准 A 机屏幕。
3. B 机实时扫描并解码，喷泉码自动补偿漏帧与乱序，进度条显示完成度。
4. 接收完成后进行 CRC/哈希校验，B 机提示"校验通过"，数据无损还原到本地。

**预期结果：** 文件在 B 机无损还原，全程无网络连接，数据只经过"屏幕 → 相机"。

### 场景 2: 同网 WiFi 加速

**前提条件：** A、B 两机在同一局域网，均已安装本工具。

**操作流程：**
1. A 机执行 send 命令，工具检测到与 B 机同网（或由用户指定），屏幕显示一个承载连接信息的二维码（握手码）。
2. B 机执行 receive 命令扫描握手码，建立局域网直传通道。
3. 数据经 WiFi 高速直传，二维码不再承载文件数据。
4. 传输完成，完整性校验通过。

**预期结果：** 数据以接近局域网带宽的速度传输，远快于纯光学；二维码仅用于握手。

### 场景 3: 手机离线中转摆渡

**前提条件：** 两台隔离电脑 A、C 不在同一处且均不联网；用户持有一台手机（可离线打开移动网页）。

**操作流程：**
1. A 机发送：屏幕播放二维码序列。
2. 手机打开移动网页，扫码接收数据并暂存在手机本地（浏览器存储）。
3. 用户走到 C 机前，手机将暂存数据编码为二维码序列并在手机屏幕上播放。
4. C 机执行 receive 扫描手机屏幕，解码还原并校验。

**预期结果：** A、C 两机无需同时在场、无需物理相邻，数据经手机离线摆渡完成传输；手机仅作暂存载体，数据不出物理边界。

### 场景 4（补充）: 终端快速传配置文本

**前提条件：** 开发者需要在两台设备间传一个短配置文件/密钥/命令/URL。

**操作流程：**
1. 发送端执行 send 传入短文本，屏幕显示单张/少量二维码。
2. 接收端（或普通手机扫码 App）扫一次即得明文。
3. 接收端工具校验后输出文本。

**预期结果：** 短文本秒级直达，无需建立连接；第三方扫码 App 也能读取纯文本二维码（兼容性）。

## 6. 功能需求详情

### F-01: CLI 命令入口

**描述：** 提供统一命令行入口，含 send 与 receive 两个核心子命令，接受文件路径或文本作为输入，输出到终端或指定路径。命令需支持关键参数（输入路径、输出目录、文本内容，以及发送/接收的速率、二维码尺寸/版本等可调参数，参数细节由架构阶段细化）。

**输入：** 文件路径 或 文本内容；可选参数（输出目录、速率、二维码尺寸等）。

**输出：** 发送端在屏幕播放二维码；接收端将数据写入指定路径/终端。

**验收标准：**
- send / receive 主命令可在目标平台运行，无 GUI 依赖。
- 支持文本与文件两类输入。
- 参数错误时给出清晰的中文提示与 usage 帮助。

**异常处理：**
- 文件不存在 / 无读取权限 → 报错并给出明确提示。
- 未指定必要参数 → 输出 usage。
- 摄像头不可用 → 接收端提示并退出。
- 目标路径不可写 → 报错。

### F-02: 光学发送

**描述：** 将载荷切块，经喷泉码编码后逐块生成二维码，按序在终端（或独立窗口）连续播放，形成二维码动画序列；支持调整播放速率与二维码尺寸以适配接收端。

**输入：** 待发送的文件字节流 / 文本；发送参数（帧率、二维码尺寸/版本、纠错冗余度）。

**输出：** 屏幕上的二维码动画序列（QR 流）。

**验收标准：**
- 能对任意二进制文件稳定生成 QR 流。
- 二维码符合标准，可被通用解码器识别。
- 播放速率可调。
- 发送过程不因个别块丢失而失败（由喷泉码兜底）。

**异常处理：**
- 载荷过大 → 提示预估时长 / 建议走同网加速（Phase 2）。
- 终端不支持高分辨率/彩色 → 降级为单色 / 较小版本二维码。
- 播放中断（Ctrl+C）→ 立即停止并释放资源。

### F-03: 光学接收

**描述：** 调用系统摄像头连续采集屏幕上的二维码，实时解码各编码块，收够足够数量块后经喷泉码还原原始数据；支持实时反馈已接收块数 / 进度。

**输入：** 摄像头视频流；接收参数（摄像头设备号、二维码尺寸/版本、期望块数或总大小）。

**输出：** 还原后的原始文件 / 文本，写入本地指定路径。

**验收标准：**
- 能从标准二维码流稳定还原数据。
- 支持漏帧 / 乱序下的还原（配合 F-04）。
- 环境光线 / 角度正常时解码成功率达标。
- 支持指定摄像头设备。

**异常处理：**
- 无摄像头 / 权限被拒 → 明确报错。
- 解码持续失败 / 无法对准 → 提示调整距离与角度。
- 中途断流 → 喷泉码补足后可继续，不足则提示重试。
- 解码到已收过的块 → 去重忽略。

### F-04: 喷泉码纠错（FEC）

**描述：** 采用喷泉码（倾向 RaptorQ / LT）对载荷编码，生成带冗余的编码块；接收端收够任意足量不同块即可无损还原，天然抗漏帧、抗顺序错乱，无需 ACK/重传；冗余度可配置。

**输入：** 载荷分块 + 冗余度参数。

**输出：** 编码块序列（供二维码承载）；接收端还原的原始载荷。

**验收标准：**
- 在存在一定比例（参考值约 10~30%）随机丢块、块乱序到达的情况下仍可无损还原。
- 冗余度可调。
- 对空载荷 / 单块载荷正确处理。
- 还原结果与原文逐字节一致（配合 F-06 校验）。

**异常处理：**
- 接收块数不足还原阈值 → 无法还原，提示并引导重试/重扫。
- 编码库异常 → 报错，可回退为无 FEC 的朴素分块（若可行）或终止。

### F-05: 文本直传

**描述：** 短文本（如配置、密钥、命令、URL）无需切块动画，直接编码为单张或少量二维码，接收端扫一次即得，低延迟直达；纯文本二维码可与第三方扫码 App 兼容读取。

**输入：** 短文本内容。

**输出：** 单张/少量二维码；接收端还原的文本。

**验收标准：**
- 短文本秒级完成（具体阈值由架构阶段定）。
- 单张二维码可被通用扫码 App 读取。
- 较长文本自动降级为多张 / QR 流。

**异常处理：**
- 文本过长 → 自动切换为文件传输路径（QR 流）并提示。
- 文本含特殊字符 / 多字节 → 正确编码还原不丢字。
- 二维码容量不足 → 自动提升二维码版本或拆分为少量多张。

### F-06: 传输进度与完整性校验

**描述：** 传输全程显示进度（已发送/已接收块数、百分比、速率）；还原完成后对结果做完整性校验（CRC / 哈希），校验通过则确认成功，失败则提示并引导重传。

**输入：** 传输过程计量数据；原始载荷的校验值（发送端计算）。

**输出：** 进度信息（终端显示）；校验结果（通过 / 失败）。

**验收标准：**
- 进度实时刷新，最终 100% 与校验结果一致。
- 校验失败时明确报错，不静默写出损坏数据。
- 支持传输结束后比对并输出哈希。

**异常处理：**
- 校验失败 → 丢弃已还原数据或标记为损坏，提示重传。
- 进度长期无新块（卡死）→ 提示并允许手动终止。
- 哈希算法不匹配 → 报错。

### F-07: 同网检测与 WiFi 加速（Phase 2，初步需求）

> 说明：Phase 2 范围，此处为初步需求，实现细节待架构阶段细化。

**描述：** 发送端检测两端是否同网（或由用户指定），同网时二维码仅承载连接信息（握手），实际数据经局域网 HTTP 临时服务直传；不可用 / 跨网时自动回退纯光学。

**输入：** 双方网络环境信息；待传数据。

**输出：** 握手二维码 + 局域网直传通道；传输结果。

**验收标准：**
- 同网时自动切换直传，吞吐显著高于纯光学。
- 跨网 / 无法直连时自动回退纯光学。
- 直传过程有完整性校验。

**异常处理：**
- 直传通道中断 → 回退纯光学或提示重试。
- 握手二维码被第三方误扫 → 一次性 token 失效（安全）。
- 临时服务端口冲突 → 自动换端口。

### F-08: 手机离线中转摆渡（Phase 2，初步需求）

> 说明：Phase 2 范围，此处为初步需求，实现细节待架构阶段细化。

**描述：** 移动网页（PWA，可离线）在手机浏览器运行，复用摄像头扫码实现"接收 → 本地暂存 → 重新编码播放"发送，手机作为离线数据摆渡站；暂存数据仅存本机、可手动清除。

**输入：** 手机摄像头扫描的 QR 流（接收）；暂存数据（发送时重放）。

**输出：** 暂存数据；手机屏幕上的二维码序列（发出）。

**验收标准：**
- 手机网页离线可用。
- 完整走通"收 → 暂存 → 发"。
- 暂存数据断电 / 刷新后仍可取出（本地持久化）。
- 支持手动删除暂存。
- 收发两端能力对称（复用光学收发核心）。

**异常处理：**
- 浏览器不支持摄像头 / 存储 → 明确提示。
- 暂存空间不足 → 提示并阻止接收。
- 页面刷新 → 暂存数据仍保留。
- 用户主动清除 → 数据彻底删除。

## 7. 非功能需求

### 性能
- 响应时间：文本直传秒级；文件传输时长取决于数据量与二维码流速率，MVP 提供进度反馈，具体吞吐目标由架构/实测细化。
- 并发量：CLI 单用户工具，无多租户/高并发要求；同网直传单会话即可。
- 数据量：文本直传面向 KB 级；文件传输 MVP 目标支持到若干 MB 级（具体上限由 QR 流时长与纠错冗余共同决定，架构阶段给出建议值）。

### 安全
- 认证方式：纯光学路径无网络、无账号体系，天然物理隔离；同网直传使用一次性临时 token/URL 作为握手凭证，防止扫描即被恶意接入。
- 权限控制：工具以本机用户权限运行，仅读写用户显式指定的文件路径，不访问无关数据。
- 数据加密：数据不经过任何第三方服务器/云端；同网直传路径在局域网内传输，建议支持（可选）会话加密；手机中转暂存数据仅存本机浏览器存储，支持手动清除，不自动上传。

### 可用性
- 可用率目标：本地工具无 7x24 在线要求；核心路径（纯光学收发）在目标平台稳定可用。
- 故障恢复：光学丢帧由喷泉码兜底自动恢复；WiFi 中断回退纯光学或提示重试；手机暂存数据本地持久化，断电/刷新不丢失；所有失败给出明确中文提示与重试引导。
- 易用性：一条命令即可收发，无需配对/安装接收端；命令帮助（usage）完整；错误信息可理解、可操作。

### 兼容性
- 平台：目标支持 Linux / macOS / Windows 终端（Go 单二进制，具体以架构选型为准）；摄像头访问依赖操作系统摄像头能力。
- 设备：发送端需屏幕、接收端需摄像头；支持无 GUI 的服务器/嵌入式设备（终端字符/块渲染二维码）。
- 标准：二维码符合标准 QR 码规范，文本直传可被第三方通用扫码 App 读取。
- 手机端（Phase 2）：现代移动浏览器（iOS Safari / Android Chrome 等），需支持摄像头与本地存储 API；PWA 支持离线使用。

## 8. 优先级定义

- P0：必须有，MVP 核心，缺失则产品不可用（对应 F-01 ~ F-06）。
- P1：重要，MVP 后立即跟进（对应 F-07 同网加速、F-08 手机中转）。
- P2：有价值，后续迭代（如加密增强、更多平台/终端适配、GUI 等，待补充）。
- P3：锦上添花，有空再做。
